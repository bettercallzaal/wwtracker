# The public API, audited against chain, 2026-09-20

For Candy. Everything here was measured today against
`wavewarz.info/api/public/*` and against the 1,694 battle accounts the program
owns. No opinions about the code, and nothing that needs a reply in any
particular form.

**The headline: the API is in better shape than a single number suggests, and
the gaps are concentrated in main events rather than spread everywhere.**

## What is served

| Endpoint | Rows | Notes |
|---|---|---|
| `/api/public/stats` | one object | live totals |
| `/api/public/battles` | **1,558** via paging | 50 by default |
| `/api/public/events` | **54** via paging | carries 173 rounds |

**`limit` and `offset` both work and neither is documented.** `limit` caps at
200 - `limit=1000` silently returns 200, which is the right behaviour and worth
writing down. Without them a consumer sees 50 rows and reasonably concludes
that is the whole dataset. Everything below was only findable because paging
was guessed at.

**404s that return a 42 KB HTML body:** `/artists`, `/songs`, `/traders`,
`/leaderboards`, `/rounds`, `/clippers`. Fine, but a consumer probing the
surface gets an HTML page where JSON was expected. A JSON 404 would be kinder.

---

## 1. 136 battles exist on chain and not in the API

    chain battle accounts   1,694
    API battles             1,558
    on chain, absent        136
    in API, not on chain    0

**The direction is the good one** - nothing is invented, only missing. By year
of battle id: **99 from 2025, 37 from 2026**, so this is not purely an old
backlog.

Anyone computing a platform total from the API is 8% low, and cannot tell.

## 2. `winnerDecided` and the program's settled byte disagree on 235 battles

    winnerDecided TRUE but never settled on chain    21
    settled on chain but winnerDecided FALSE        214

**The 21 are the ones that bite.** A claim against them returns
`BattleNotEnded (6009)` while the site says the winner is decided. Battle
1787568630 was the worked example; six more were settled by hand on 2026-09-19
and six more on 2026-09-20 after being found this way.

The 214 in the other direction are harmless but make `winnerDecided` unusable
as a settlement signal.

**These are two different facts and the API presents one of them.** A
`settledOnChain` boolean beside `winnerDecided` would close it.

## 3. Two incompatible `factors` schemas share one field name

This is the finding with the most consequence for anyone building on the API,
and nothing announces it.

| Battle type | Rows | `factors` keys |
|---|---|---|
| `quick` | 1,340 | `djWavyWinner`, `djWavyReasoning`, `pollWinner`, `pollVotesArtist1`, `pollVotesArtist2` |
| `main` + `community` | 218 | `humanJudgeWinner`, `xPollWinner`, `solVoteWinner`, `judgedAt` |

**No key is shared between them.** A consumer reading `factors.pollWinner` gets
data on quick battles and `undefined` on every main event, with no error and no
type change to warn them. The split is clean and correct in substance - quick
battles are judged by DJ Wavy, main events by a human panel - but two schemas
under one name is the kind of thing that is discovered in production.

**Fill rates differ enormously between them:**

| Schema | Field | Filled |
|---|---|---|
| quick, 1,340 rows | `djWavyWinner` | **78%** |
| | `djWavyReasoning` | 58% |
| | `pollWinner` | 47% |
| main/community, 218 rows | `humanJudgeWinner` | **6%** |
| | `xPollWinner` | **6%** |
| | `solVoteWinner` | **6%** |
| | `judgedAt` | **6%** |

**Quick battles are well covered. Main events are not** - 206 of 218 carry no
judge data at all, and those are the curated events with the audience.

## 4. The charts judge cannot be reconstructed for any quick battle

The quick schema has **no SOL or charts field**. `pollWinner` and
`djWavyWinner` are there; the third judge is not.

So the 2-of-3 rule cannot be verified from the API for **1,340 of 1,558
battles**, even where both other judges are recorded.

**This one is free to fix.** The charts winner is the larger pool and it is on
chain for every settled battle with no exception in 1,482 checked. It does not
need a new measurement, only a field.

## 5. The volume field carries the pool value on 15 rounds

Of the 173 rounds `/events` exposes, **15 report volume exactly equal to pool on
both sides**, to four decimal places, above a 0.0034 SOL rounding floor.

    1751420288  1751421607  1753063414  1757207855  1757211619
    1757898875  1758505532  1760574699  1760576678  1760663446
    1760666134  1761788317  1762740734  1764205612  1764207785

**4.64 SOL of volume reported as pool.** A buy puts 98.5% of its SOL into the
pool, so the two are never equal on a battle that traded - 156 of the 173 rounds
show the healthy shape where volume exceeds pool.

Detail, the four rows that regressed between scans, and the one question worth
asking your own logs: `docs/upstream/volume-field-2026-09-19.md`.

## 6. `artistPayouts.note` understates the artist's own rate

> "Instant, automatic onchain payouts to artists - **1% of trading volume** +
> settlement bonus"

**Measured at exact lamports on eight real transactions, four buys and four
sells: the total trade fee is 1.500% and it splits 67/33, so the artist takes
1.005%.** Not 1.00%.

The difference is small and it is in the artist's favour, so the note
undersells the product. The PRD and `wavewarz-math.ts` say 1.00/0.50 as well;
the program does not.

Verified on both legs, which had not been done before today: **a sell pays the
same 1.500%, split the same 67/33**, and a claim pays nothing.

## 7. Smaller things

**`/events` returns 54, `stats.battles.mainEvents` says 61.** A 7 gap between
two numbers in the same API.

**`winnerSide` is null on 255 battles (16%)** and the field is the only one
with a null rate above zero on a battle row. Some are genuinely undecided; the
21 from section 2 are not.

**Battles do not link to events.** A round carries `battleId`, so
event -> battle works; there is no `eventId` on a battle row, so battle -> event
does not. Reconstructing it means walking every event's rounds.

**`volume.last24hSol` reads 0.0** with `last7dSol` at 3.19. True at a quiet
moment, but indistinguishable from a broken window.

---

## The five that would help a consumer most, in order

1. **Document `limit` and `offset`**, and the 200 cap. Everything else here was
   only reachable by guessing them.
2. **Add `solVoteWinner` to the quick schema.** It is derivable from chain and
   it is the missing third of a 2-of-3 rule on 86% of the dataset.
3. **Expose `settledOnChain` beside `winnerDecided`.** Two facts, presented as
   one, and 21 battles where the difference is load-bearing.
4. **Backfill the 206 main and community events with no judge data** - or say
   the data does not exist, which is equally useful and stops people looking.
5. **Name the two `factors` schemas**, or split them into two fields. A
   consumer currently learns about the second one when their code returns
   `undefined` in production.

## Reproduce any of it

Paging, which is the part nothing documents:

```
curl -s 'https://wavewarz.info/api/public/battles?limit=200&offset=0'
curl -s 'https://wavewarz.info/api/public/events?limit=200&offset=0'
```

The chain side is a single `getProgramAccounts` against
`9TUfEHvk5fN5vogtQyrefgNqzKy2Bqb4nWVhSFUg2fYo` filtered to `dataSize: 353`,
reading battle id at offset 8, pools at 212 and 220, the winner flag at 244 and
the settled byte at 245. **Offset 220 is the B pool, not 228** - our own tooling
documented 228 and disagreed with 30 real accounts.
